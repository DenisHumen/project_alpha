# ADR-0018: Провайдеры метаданных — трейт `Provider` в ядре, блокирующий HTTPS в `pa-metadata`

- **Статус:** Принят
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** META-009 (реализация), META-010…012, META-013, META-025; DEC-008 и ADR-0011 §6 (ключ TMDB); ADR-0001 (Rust-ядро); `docs/research/03-metadata-recognition.md` §4.7, §7.2; `docs/legal/providers.md` (TMDB)

## Контекст и проблема

Распознавание (`pa-recognition`) — sans-IO: сеть снаружи ядра, а eval гоняется офлайн на записанных ответах (03 §7.2). В `pa-eval` уже был свой трейт `Provider` с нейтральным запросом `{provider, endpoint, params}` и кассетами record/replay. META-009 добавляет первый живой провайдер (TMDB), и нужно решить: где живёт трейт, каким HTTP-стеком ходить в сеть, где кэш и как обращаться с ключом, если ключа проекта ещё нет. Ограничения: ADR-0005 и `cargo deny` (без GPL, без OpenSSL), Android и десктоп из одного кода, условия TMDB (атрибуция, кэш не дольше 6 месяцев, 429).

## Факторы решения

- Ядро детерминировано: одни и те же запросы к живому провайдеру и к кассете.
- Один TLS-стек на все платформы, включая Android, без JNI-инициализации и без OpenSSL.
- Тесты без сети и без реального ключа; ключ внедряется.
- Минимум новых зависимостей; лицензии из списка ADR-0005.

## Рассмотренные варианты

1. Трейт в `pa-recognition`, клиенты в новом `pa-metadata`, блокирующий `ureq` + rustls (ring) + `webpki-roots`.
2. То же, но асинхронный `reqwest` на tokio из `pa-runtime`.
3. HTTP делает Dart (уже есть клиент TMDB в `pa_library`), Rust получает только JSON через колбэк.

## Решение

Выбран вариант **1**.

- **Граница.** `pa_recognition::provider::{Provider, ProviderRequest, ProviderError}` — sans-IO типы ядра (serde + serde_json, без I/O). `pa-eval` их реэкспортирует, кассеты и `RecordingProvider` остаются в `pa-eval`. `ProviderError` расширен: `Unavailable` (нет ключа или сети — ядро продолжает на локальном распознавании), `RateLimited`, `NotFound`, `BadRequest`.
- **Крейт `core/crates/pa-metadata`** (workstream META): `HttpTransport` (только `GET`), `UreqTransport` за фичей `http` (по умолчанию), HTTP-кассеты `ReplayTransport`/`RecordingTransport`, `RateLimiter` (token bucket) и `RetryPolicy`, `ProviderCache`, ключи, атрибуция, клиент TMDB. Клиент блокирующий, `Send + Sync`, методы `&self`; из async-кода — через пул блокирующих задач. Трейт `Provider` синхронный, как и в `pa-eval`.
- **TLS:** `ureq` 3 с фичей `rustls` (провайдер ring) и корнями Mozilla из `webpki-roots`. Лицензия `webpki-roots` — CDLA-Permissive-2.0: добавлено узкое исключение в `deny.toml` только для этого крейта.
- **Лимиты TMDB:** свой лимит 20 запросов/с с burst 20 (половина опубликованных ~40/с); 429 → `Retry-After` или экспонента 1, 2, 4, 8 с (до 30 с), пауза для всех потоков клиента, до 4 повторов; 5xx — те же повторы; 401/404 не повторяются.
- **Кэш** (`ProviderCache`): ключ без учётных данных; свежесть — поиск 1 день, фильмы/завершённые сериалы/переводы/ID/картинки 14 дней, идущие сериалы 1 день, сезоны и episode groups 3 дня; устаревшая запись отдаётся, если сети, ключа или квоты нет; **жёсткий предел 182 дня** — запись старше не отдаётся и удаляется `purge_expired`, `purge_all` стирает все данные TMDB (прекращение лицензии). Реализации: память и отдельный SQLite-файл в каталоге кэша (не в БД медиатеки — кэш одноразовый).
- **Ключ** (DEC-008): ключ проекта читается при **компиляции** из `PA_TMDB_API_KEY` (Secrets окружений `release`/`store` или `.env.local`), в git не попадает; «свой ключ» пользователя всегда главнее и меняется на лету; v3-ключ уходит в `api_key`, v4-токен — в `Authorization: Bearer`. Сборка без ключа (F-Droid, контрибьюторы) работает: клиент отвечает `NoKey`/`Unavailable` или кэшем. В `Debug`, ключах кэша, кассетах и текстах ошибок ключа нет.
- **Фикстуры** синтетические: форма ответов TMDB v3, выдуманные работы и ID. Настоящие ответы TMDB в git не кладём (условия: кэш ≤ 6 месяцев, без сублицензирования).

Не входит: AniList/Shikimori/AniDB/TVDB (META-010…012), FFI/FRB-экспорт клиента и замена Dart-клиента в `pa_library` (отдельная задача), перезапись кассеты бейзлайнов `pa-eval` живым TMDB (META-025, нужен ключ).

### Последствия

- Хорошо: один код запросов для приложения, сервера и eval; любой живой провайдер записывается в кассету `pa-eval` без адаптеров; тесты быстрые и без сети.
- Хорошо: TLS одинаков везде, OpenSSL и aws-lc не тянутся (`cargo deny` зелёный).
- Плохо: корни сертификатов обновляются только с выпуском приложения (не системное хранилище). Корпоративные MITM-прокси с собственным CA не поддерживаются.
- Плохо: блокирующий клиент занимает поток на время запроса; при сотнях параллельных запросов нужен пул, но лимит 20/с всё равно ограничивает параллелизм.
- Нейтрально: ключ проекта извлекаем из бинаря — поэтому «свой ключ» обязателен (providers.md §1).

## Плюсы и минусы вариантов

### Вариант 2 (`reqwest` + tokio)

- Плюс: неблокирующий, готов к большому параллелизму.
- Минус: заметно больше зависимостей (hyper, h2, tower), трейт `Provider` пришлось бы делать async и в ядре, и в `pa-eval`, ядро потеряло бы простоту sans-IO-вызова.

### Вариант 3 (HTTP в Dart)

- Плюс: нет TLS в Rust.
- Минус: сервер и инструменты (`pa-eval`, META-025) без Flutter остаются без провайдера; логика лимитов и кэша дублировалась бы на двух языках.
