# ADR-0039: Удалённый конфиг — подписанный minisign JSON из публичного репо, `minisign-verify`, anti-rollback по `serial`

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `CORE-014`, `TWI-004`, [ADR-0004](0004-no-project-servers-local-sync.md), [ADR-0018](0018-metadata-providers-blocking-http.md), `docs/research/06` §2.6–2.7, [docs/dev/remote-config.md](../dev/remote-config.md)

## Контекст и проблема

Twitch GQL (client-id, хэши persisted queries, требование integrity-токена) может измениться за день (06 §2.6). Приложению нужны флаги и kill-switch'и, которые меняются без релиза. Своего сервера у проекта нет (ADR-0004), поэтому конфиг — статический файл в публичном репозитории. Раз файл раздаёт чужая инфраструктура (GitHub, CDN), доверять ему можно только по подписи владельца.

## Факторы решения

- Без серверов проекта; только статика (raw.githubusercontent.com, GitHub Pages).
- Подлинность не зависит от GitHub: подменённый или устаревший файл не принимается.
- Работа офлайн: последняя валидная копия, а без неё — встроенная.
- Чистый Rust, лицензия из allow-list ADR-0005, без OpenSSL; один HTTP-стек с `pa-metadata` (ureq + rustls).
- Владелец подписывает простым офлайн-инструментом, секретный ключ не попадает в CI.

## Рассмотренные варианты

1. **minisign** (Ed25519) и крейт [`minisign-verify`](https://crates.io/crates/minisign-verify) 0.3 (MIT, без зависимостей) только для проверки.
2. `ed25519-dalek` и свой формат подписи.
3. Подпись Sigstore/cosign (keyless через OIDC).
4. Без подписи, только HTTPS до GitHub.

## Решение

Выбран вариант **1**: стандартный инструмент для владельца (`minisign -S`), маленький крейт без зависимостей для проверки; свой формат (2) — лишний код и инструменты, cosign (3) тянет большой стек и онлайн-инфраструктуру, вариант 4 доверяет GitHub/CDN целиком.

Конкретика (крейт `pa-remote-config`):

- Файлы: `config/remote-config.json` + `config/remote-config.json.minisig`. Зеркала по порядку: raw `main`, затем GitHub Pages.
- Принимаются только prehashed-подписи (`ED`); доверенный комментарий обязан содержать `file:<имя>` — подписанный файл нельзя выдать за другой.
- Порядок: подпись → разбор JSON. Неподписанные байты не разбираются.
- `serial` монотонный: документ с меньшим `serial`, чем текущий (в том числе встроенный), отвергается — защита от отката kill-switch'а повтором старого подписанного файла.
- `schema` выше поддерживаемой отвергается; неизвестные поля игнорируются.
- Кэш — один файл (тело, подпись, ETag, URL, время проверки), запись через временный файл и rename; при загрузке подпись проверяется заново. Ошибка обновления не трогает ни текущие флаги, ни кэш.
- `If-None-Match` с ETag того же URL; `304` не скачивает подпись повторно.
- Политика обновления — в самом документе, с жёсткими пределами (15 мин … 7 дней, повтор ≥ 5 мин).
- Публичный ключ — константа `PRODUCTION_PUBLIC_KEY`. Пока это заглушка, клиент работает только на встроенной копии во всех сборках; `just core remote-config-release-check` падает. Тесты подписывают одноразовым ключом, созданным в самом тесте.
- Flutter получает фасад `CoreRemoteConfig` через `pa-frb` (флаги синхронно, обновление асинхронно); UniFFI-фасад — по мере надобности нативным клиентам.

### Последствия

- Хорошо: ноль инфраструктуры; подмена файла на GitHub/CDN ничего не даёт; конфиг работает офлайн; формат проверяется теми же правилами в приложении и в `just core remote-config-verify`.
- Плохо: потеря или утечка секретного ключа лечится только релизом с новым ключом; задержка CDN raw (до ~5 мин) может временно рассинхронизировать файл и подпись (клиент повторит позже); нет защиты от «заморозки» (злоумышленник может не давать клиенту обновиться) — только от отката.
- Требует работы: владелец создаёт ключ и подписывает конфиг; TWI-004 заполняет раздел `twitch` и использует `CoreRemoteConfig::twitch()`.

## Открытые вопросы (решения владельца)

- Где живёт секретный ключ: офлайн у владельца (рекомендация) или Secret окружения публикации конфигов (как сейчас записано в secrets.md).
- Подключать ли `remote-config-release-check` в релизный workflow до появления ключа.
- Включить ли GitHub Pages для `config/` (второе зеркало) и один ли файл на всё (рекомендация: да, раздел `twitch` внутри `remote-config.json`) или отдельный `config/twitch/…`, как сказано в TWI-004.
