# ADR-NNNN: Медиасервер — HTTPS с самоподписанным сертификатом, pinning по `fp` из mDNS, порт 8487

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `SRV-004`, `NET-009`, `SRV-006`, `DIST-*`, `docs/research/04` §1.6, §1.7, §5.2, [ADR-0019](0019-lan-discovery-mdns.md), [ADR-0004](0004-no-project-servers-local-sync.md)

## Контекст и проблема

Медиасервер (режим B) работает у пользователя в LAN: на ПК или в нашей NAS-ОС. Нужен шифрованный транспорт без нашего облака и без публичного CA (у сервера нет доменного имени), клиент должен отличить свой сервер от подменённого. ADR-0019 оставил формат TXT `fp` за SRV-004. Кроме того, черновой порт 8096 совпадает с Jellyfin/Emby: на одной машине оба сервера не уживаются, а клиенты путают их при ручном вводе адреса.

## Факторы решения

- Работа полностью офлайн, без нашего облака и ACME (ADR-0004).
- Защита от подмены сервера в LAN после первого подключения.
- Только rustls и pure-Rust зависимости с разрешёнными лицензиями (`deny.toml`).
- Пользователь может сверить отпечаток вручную привычными инструментами.
- Совместная работа с популярными домашними сервисами на одном хосте.

## Рассмотренные варианты

1. Самоподписанный сертификат, pinning отпечатка сертификата (SHA-256 DER) по TOFU.
2. Самоподписанный сертификат, pinning SPKI (хэш открытого ключа).
3. Сертификат через свой ACME/DNS-сервис (`<hash>.pa-direct.net`, как `plex.direct`).
4. Plain HTTP в LAN.

## Решение

Выбран вариант **1**.

- **TLS по умолчанию.** rustls 0.23 с провайдером `ring`, TLS 1.2 и 1.3, ALPN `http/1.1`. При первом старте `rcgen` создаёт ECDSA P-256 сертификат (CN «Kinolune media server», SAN `localhost` и `pa-<id>.local`) в `<data_dir>/tls/server.crt` и `server.key` (ключ — права 0600, запись через временный файл). Свои файлы — `[tls] cert` и `key`. HTTP без TLS — только явной опцией `[tls] enabled = false` / `ALPHA_MEDIA_TLS=off` (старые ТВ и плееры, §5.2).
- **Формат `fp`:** `sha256:<64 hex в нижнем регистре>` от DER листового сертификата. Это то же значение, что печатает `openssl x509 -noout -fingerprint -sha256` (без двоеточий), — пользователь может сверить его руками; Syncthing идентифицирует устройства так же. Парсер принимает и верхний регистр, и двоеточия.
- **Pinning в клиенте** — `pa-discovery`, фича `tls`: `Fingerprint`, `check_pin` (TOFU: `FirstUse` → сохранить, `Match`, `Changed` → не доверять молча, спросить пользователя) и `PinnedVerifier` — `rustls::ServerCertVerifier`, который принимает ровно один лист по отпечатку и не проверяет имя, издателя и сроки, но проверяет подписи рукопожатия (подходит только владелец ключа). Хранит пины приложение (по `id` сервера); клиент сервера — `SRV-006`.
- **mDNS-анонс** — `pa_discovery::Advertiser`, тип `_projectalpha._tcp`, TXT по `ServerTxt`: `txtvers=1`, `id` (UUID хаба синхронизации — один стабильный id сервера), `v=1`, `name` (из `[discovery] name`, иначе имя хоста), `fp`. Сервер на loopback-адресе не анонсируется; сбой mDNS логируется и не роняет сервер. Выключение — `[discovery] enabled = false` / `ALPHA_MEDIA_MDNS=off`.
- **Порт по умолчанию — 8487/tcp** (HTTPS и, при выключенном TLS, HTTP на том же порту). Диапазон 8475–8499 не занят в реестре IANA; порт не используют Jellyfin/Emby (8096, 8920), Plex (32400), Syncthing (8384, 22000), админки NAS (5000/5001, 8080), Transmission (9091), *arr (7878, 8989, 8686, 9696). Заглушка NAS-ОС (`distro/`) и открытый порт firewalld переведены на 8487.

Отклонено: SPKI-pinning (2) переживает перевыпуск сертификата с тем же ключом, но клиенту нужен разбор X.509, а пользователь не сверит значение стандартными командами; перевыпуск без смены ключа нам пока не нужен. ACME-домен (3) требует нашего DNS-сервиса — противоречит ADR-0004; можно добавить позже как опцию для веб-доступа. Plain HTTP (4) — только по явной опции.

### Последствия

- Хорошо: шифрование и защита от подмены без облака и без настроек; отпечаток виден в логе старта и в TXT.
- Хорошо: сервер уживается с Jellyfin/Plex на одной машине.
- Плохо: браузер и `curl` без `-k` ругаются на самоподписанный сертификат; веб-админке (`server/web/`) понадобится объяснение или ACME-вариант.
- Плохо: удаление `<data_dir>/tls` меняет отпечаток — сопряжённые клиенты увидят `Changed` и спросят пользователя (это и есть поведение TOFU).
- Плохо: первый контакт (TOFU) не защищён от активной атаки в LAN; сверка отпечатка или QR-сопряжение (SRV-003) это закрывают.
- Требует работы: `SRV-006` — клиент в ядре хранит пины и подключается через `PinnedVerifier`; NAS-ОС — проверки здоровья настоящего сервера по `https://` с `-k` вместо заглушки.
