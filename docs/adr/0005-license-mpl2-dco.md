# ADR-0005: Лицензия кода MPL-2.0 и DCO вместо CLA

- **Статус:** Принят (решение владельца `DEC-002`)
- **Дата:** 2026-11-13
- **Решают:** владелец проекта
- **Связано:** `DEC-002`, `REPO-002`, `LEGAL-…`, `docs/STRATEGY.md` §5, `docs/research/02` §3, `LICENSE`, `CONTRIBUTING.md`

## Контекст и проблема

Проект открытый и принимает внешние PR. Нужно выбрать лицензию кода и способ подтверждать право контрибьютора отправить код. Ограничения:

- Приложения публикуются в App Store. Условия Apple считаются «дополнительными ограничениями», несовместимыми с GPL (прецедент — VLC, 2011).
- Клиенты динамически линкуют LGPL-библиотеки: FFmpeg, mpv (`-Dgpl=false`), libsmb2, libnfs.
- Хочется, чтобы улучшения наших файлов оставались открытыми, но без отпугивания контрибьюторов CLA.

## Факторы решения

- Совместимость с App Store и Google Play.
- Совместимость с LGPL-зависимостями и возможность объединения с GPL (desktop-сборки).
- Защита от закрытых форков наших файлов.
- Низкий порог для внешних контрибьюторов.

## Рассмотренные варианты

1. **MPL-2.0 + DCO.**
2. GPL-3.0 + DCO.
3. GPL-3.0 + CLA (право мейнтейнера перелицензировать для сторов).
4. Apache-2.0 или MIT + DCO.

## Решение

Выбран вариант **1** (владелец, `DEC-002`).

- Весь код проекта лицензирован под **MPL-2.0** (файл `LICENSE`).
- В каждом новом исходнике — заголовок `SPDX-License-Identifier: MPL-2.0` в синтаксисе языка; соответствие проверяет `reuse lint` (`REPO-002`).
- Каждый коммит подписан по **DCO 1.1** (`Signed-off-by`, `git commit -s`); проверка DCO обязательна для мержа. CLA не используем.
- За вклад, подготовленный AI-агентом, отвечает и подписывает DCO человек, запустивший агента; агент указывается трейлером `Co-Authored-By`.
- Зависимости — только с совместимыми лицензиями: MIT, Apache-2.0, BSD, ISC, MPL-2.0, LGPL (только динамическая линковка). GPL-код в клиенты не добавляется. FFmpeg и mpv — только LGPL-сборки (`--disable-gpl --disable-nonfree`, mpv `-Dgpl=false`), предпочтительно LGPL-2.1+.
- Ассеты и данные (иконки, дизайн, датасеты) могут иметь собственные лицензии; они фиксируются через REUSE (`LICENSES/`, `REUSE.toml`), а несовместимые данные в продукт не попадают (см. ADR-0006 про eval-корпус).

### Последствия

- Хорошо: можно публиковать в App Store без отдельного согласия каждого контрибьютора; изменения наших файлов остаются открытыми (файловый копилефт); MPL-2.0 допускает объединение с GPL-кодом в отдельных сборках.
- Плохо: MPL слабее GPL — можно построить закрытый продукт, используя наши файлы без изменений как библиотеку. Это сознательная цена совместимости со сторами.
- Требует работы: `REPO-002` (SPDX, REUSE), DCO-проверка в CI, `cargo deny` и проверка лицензий Flutter/SwiftPM-зависимостей, экран «Лицензии» в приложении, публикация исходников и патчей LGPL-библиотек.

### Как проверяем соблюдение

- `reuse lint`, DCO-проверка и `cargo deny` обязательны для мержа (критерий выхода M0).
- CI проверяет лицензию собранного FFmpeg (`avutil_license()` = «LGPL version 2.1 or later»).

## Плюсы и минусы вариантов

### GPL-3.0 + DCO

- Плюс: сильнейшая защита от закрытых форков.
- Минус: конфликт с App Store, как только появляется чужой код без отдельного согласия (история VLC).

### GPL-3.0 + CLA

- Плюс: мейнтейнер может выдать App Store-исключение.
- Минус: CLA отпугивает контрибьюторов; асимметрия прав подрывает доверие к open source-проекту.

### Apache-2.0 / MIT

- Плюс: максимальная совместимость, явный патентный грант у Apache.
- Минус: изменения можно закрыть — нет даже файлового копилефта.
