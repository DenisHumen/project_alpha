# ADR-0021: Аниме-провайдеры AniList и Shikimori — GraphQL `POST` в общем транспорте, общий конвейер запросов

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** META-010 (реализация), META-009 и [ADR-0018](0018-metadata-providers-blocking-http.md) (дополняет), META-011, META-012; `docs/research/03-metadata-recognition.md` §3.2, §4.3, §4.7; `docs/legal/providers.md` (AniList, Shikimori)

## Контекст и проблема

ADR-0018 сделал `HttpTransport` в `pa-metadata` «только `GET`»: TMDB — чистый REST. AniList — только GraphQL, а GraphQL-запросы по стандарту уходят `POST` с JSON-телом. Нужно решить: как отправлять `POST`, не заводя второй HTTP-клиент; как записывать такие запросы в кассеты и ключи кэша; как соблюдать лимиты, которые у двух провайдеров устроены по-разному (AniList — адаптивный 30–90 в минуту с заголовками `X-RateLimit-*` и таймаутом 1 минута после 429; Shikimori — 5 в секунду и 90 в минуту, обязательный User-Agent с именем OAuth-приложения); и не копировать в каждый клиент логику кэша, повторов и отката на устаревший кэш из TMDB.

## Факторы решения

- Один HTTP-стек (`ureq` + rustls) на все платформы, как в ADR-0018.
- Кассеты и ключи кэша без учётных данных, читаемые и устойчивые к косметическим правкам запроса.
- Лимиты соблюдаются строго в любом окне (проверяется нагрузочным тестом на ручных часах), а не только «в среднем».
- Условия AniList: без «хранилища данных» и массового сбора; условия Shikimori: User-Agent с именем приложения, без парсинга сайта.
- Минимальные правки уже принятого кода TMDB.

## Рассмотренные варианты

1. `HttpTransport::post_json` с реализацией по умолчанию «не поддерживается»; GraphQL-тело в кассете и ключе кэша сводится к операции и переменным; общий конвейер `fetch::Fetcher` для новых провайдеров.
2. Поле `method`/`body` в `HttpRequest`.
3. AniList через `GET` с `?query=` в URL.
4. Shikimori через GraphQL вместо REST.

## Решение

Выбран вариант **1**.

- **Транспорт.** В трейт `HttpTransport` добавлен `post_json(&HttpRequest, &str)`; реализация по умолчанию возвращает `TransportError` без сети, поэтому старые реализации компилируются без изменений. `UreqTransport`, `ReplayTransport` и `RecordingTransport` его поддерживают. `POST` используется только для GraphQL-*запросов* на чтение; мутаций нет.
- **Канонический ключ `POST`:** `HttpRequest::canonical_post` = путь и query + JSON-тело. GraphQL-тело (`{"query", "variables"}`) сводится к `graphql:<Операция><переменные>` (ключи отсортированы): идентичность GraphQL-запроса — операция и переменные, как путь и query у REST. В кассете это `{"path":"/","graphql":{"operation":"Search","variables":{…}}}`; текст запроса в кассету и кэш не попадает. Обратная сторона: если поменять набор полей в запросе, кассета сама не устареет — форму ответа сверяем на живом API (README кассет).
- **Общий конвейер** `pa_metadata::fetch`: кэш → токен лимитера → повторы 429/5xx (429 ставит паузу всему клиенту) → откат на устаревшую запись моложе 182 дней; ошибки — общий `FetchError` с отображением в `ProviderError`. Особенности провайдера — через внутренний трейт `Hooks` (заголовки квоты, текст ошибки, «ошибка в теле 200», TTL). Клиент TMDB не переписан: он остаётся на своём коде с ключами; перевод его на `fetch` — по желанию отдельной задачей.
- **Лимиты.** `RateLimit::per_minute(n, burst)` задаёт скорость `(n − burst)/60`, так что в любом 60-секундном окне не больше `n` запросов; у лимитера появился `set_limit`. AniList: старт 30/мин (burst 2), подстройка по `X-RateLimit-Limit` до потолка 90 и вниз до объявленного; `X-RateLimit-Remaining: 0` — пауза до `X-RateLimit-Reset`; `Retry-After` уважается до 65 с (не режется до 30 с, как у TMDB). Shikimori: `per_minute(90, 3)` — не больше 90 в минуту и 4 в секунду; User-Agent `Kinolune/<версия> (+ссылка на репозиторий)` в каждом запросе.
- **Shikimori — REST v1** (`/animes`, `/animes/{id}`, `/animes/{id}/related`): ID аниме в Shikimori — это MAL ID, поэтому русское название и описание получаются одним `GET` по MAL ID из маппингов (`pa-anime-mappings`) без поиска. Описание очищается от BB-разметки. Базовый адрес — `https://shikimori.io/api` (старый `shikimori.one` редиректит), настраивается.
- **Кэш:** поиск 1 день, вышедшие тайтлы 14 дней, онгоинги и анонсы 1 день, всё не дольше 182 дней; `purge_all` по провайдеру. Запросы — только по требованию для файлов пользователя, без обхода каталога (AniList запрещает hoarding).
- **18+:** AniList — `isAdult: false` в поиске и отсев в связях и `Media`; Shikimori — `censored=true` в поиске и скрытие `rating = rx`. Включается настройкой только для `full`-сборок.
- **Фикстуры синтетические**, настоящие ответы провайдеров в git не кладём.

### Последствия

- Хорошо: один HTTP-клиент; любой будущий GraphQL-провайдер (в том числе GraphQL Shikimori) пишется тем же путём; кассеты короткие и читаемые.
- Хорошо: лимиты доказуемо соблюдаются в каждом окне, а не в среднем; AniList сам ускоряется, когда снимет деградированный режим.
- Плохо: два варианта конвейера (TMDB и `fetch`) живут параллельно, пока TMDB не переведён.
- Плохо: лимитер на процесс, а не на IP: несколько экземпляров приложения в одной сети делят квоту AniList и могут получить 429 — на это есть пауза по `X-RateLimit-Reset`/`Retry-After` и откат на кэш.
- Нейтрально: имя OAuth-приложения Shikimori должно совпасть с `Kinolune` в User-Agent — регистрация на владельце (providers.md).

## Плюсы и минусы вариантов

### Вариант 2 (`method`/`body` в `HttpRequest`)

- Плюс: один метод `send` вместо двух.
- Минус: ломает все литералы `HttpRequest` и принятый контракт ADR-0018 ради одного провайдера.

### Вариант 3 (AniList через `GET`)

- Плюс: транспорт не меняется.
- Минус: `GET` для GraphQL AniList не документирован; длинные запросы в URL; риск, что перестанет работать без предупреждения.

### Вариант 4 (Shikimori через GraphQL)

- Плюс: Shikimori рекомендует GraphQL.
- Минус: для единственного нужного сценария (русское название и описание по MAL ID) REST v1 даёт ответ одним `GET`; GraphQL можно добавить позже тем же `post_json`.
