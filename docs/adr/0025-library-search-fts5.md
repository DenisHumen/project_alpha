# ADR-0025: Поиск по медиатеке — SQLite FTS5 с ключами из Rust и очередью на триггерах

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-008 (реализация), UI-011 (экран поиска), META-007 и [ADR-0022](0022-local-title-index.md) (нормализация названий), [ADR-0016](0016-library-sqlite-schema-refinery.md) (схема); `docs/research/01-*` §1.5, `docs/research/06-*` §5.3

## Контекст и проблема

Нужен поиск «по мере ввода» по всей медиатеке: фильмы, сериалы, аниме, эпизоды, нераспознанные видео, музыка, коллекции (позже — люди и Twitch). Запрос на русском должен находить латинские имена файлов (`ирония судьбы` → `Ironiya.sudby…`) и наоборот, алиасы (`Ведьмак` → *The Witcher*), без учёта регистра и диакритики. Цель — меньше 50 мс на 50 000 элементов. Медиатека уже лежит в SQLite (`pa-library`), а нормализация названий уже есть в `pa_recognition::title`.

## Рассмотренные варианты

1. FTS5 со своим токенизатором (C-API токенизатора из Rust).
2. FTS5 над ключами, посчитанными в Rust; пересчёт по очереди, которую ведут SQL-триггеры.
3. FTS5 над ключами из Rust, обновление явными вызовами из каждого места записи (сканер, матчер, музыка).
4. Индекс в памяти (как `TitleIndex` из ADR-0022) или `tantivy`.

## Решение

Выбран вариант **2**.

- Каждая строка (название, алиас из `titles`, имя файла и его папки, артист, альбом, трек, коллекция) — документ `search_docs` с ключами *plain* (свёртка регистра и диакритики, римские цифры) и *loose* (транслит кириллицы и сведение вариантов написания из `pa_recognition::title::normalize`). Ключи считает Rust, поэтому индекс и запрос нормализуются одной и той же функцией.
- `search_fts` — contentless FTS5 (`contentless_delete`) с префиксными индексами; токенизатор `unicode61` только режет готовые токены по пробелам.
- Триггеры на `works`, `titles`, `episodes`, `files`, `matches`, музыкальных таблицах и `collections` кладут изменённую сущность в `search_queue`. `search::sync` пересобирает документы сущностей из очереди; `search::search` вызывает его сам, если очередь не пуста. Писателям не нужно знать о поиске, а соединение без Rust (например, `sqlite3`) не ломает базу: индекс догонит при следующем поиске.
- Ранжирование — в Rust по кандидатам из FTS5 (bm25) и из точного и префиксного поиска по ключам: точное название > название начинается с запроса > все слова где-то в названии; затем доля названия, покрытая запросом, вес алиаса и вид результата. Один результат на сущность, группировка по виду.

### Последствия

- Хорошо: без новых зависимостей; одна нормализация с распознаванием; индекс на диске, не строится при запуске; на 50 000 элементах самый медленный запрос (одна буква) — 14 мс, обычные — 2–4 мс (release).
- Плохо: первый поиск после большой записи платит за `sync` (≈0,03 мс на сущность в release: 50 000 сущностей — 1,4 с на сервере сборки), поэтому сканеру стоит вызывать `sync` после партии; поиск пишет в базу (нужно соединение на запись); ключи хранятся дважды (в `search_docs` и в индексе FTS5).
- Изменение правил нормализации требует `search::rebuild`.
