# ADR-0013: Делать `pa-vfs` синхронным, объектно-безопасным и с позиционным чтением

- **Статус:** Принят
- **Дата:** 2026-11-13
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** NET-001, NET-002…NET-008, NET-019, CI-012, LIB-003, LIB-004; [ADR-0001](0001-rust-core-uniffi-frb.md), [ADR-0003](0003-native-player-surfaces-engines.md); `docs/research/02` §1.4, §4; `docs/research/04` §1.3

## Контекст и проблема

`pa-vfs` — общий интерфейс для всех мест, где лежат медиа: локальная папка, SMB (libsmb2, C), NFS (libnfs, C), WebDAV (reqwest, async), SFTP (russh, async), FTP. Потребители тоже разные: сканер (обход дерева), prober и отпечатки (OSHash: два чтения в начале и конце файла), loopback HTTP Range-прокси (tokio), адаптеры FFmpeg `AVIOContext` и mpv `stream_cb` — это синхронные C-колбэки на потоке плеера, Media3 `DataSource` — синхронный Java-интерфейс. Нужно выбрать форму трейтов до того, как появятся бэкенды, иначе каждый из них придётся переделывать.

## Факторы решения

- Плееры читают через синхронные колбэки на своих потоках (FFmpeg, mpv, Media3).
- Одно открытое видео читают параллельно: демуксер, prefetch, иногда два потока прокси.
- Бэкенды разнородны: C-библиотеки с блокирующим API и async-крейты.
- Менеджер источников хранит источники разных типов в одной коллекции → нужен `dyn Vfs`.
- Трейт-крейт не должен тащить рантайм и зависимости в каждый бэкенд и в FFI.

## Рассмотренные варианты

1. Async-трейты (`async fn` в трейтах или `async-trait`).
2. Синхронные трейты с курсором (`Read + Seek`).
3. Синхронные трейты с позиционным чтением `read_at(&self, offset, buf)` без курсора.

## Решение

Выбран вариант **3**: он без адаптеров подходит синхронным колбэкам плееров и позволяет читать один источник из нескольких потоков, а async-потребители оборачивают вызов в `spawn_blocking`.

Конкретика:

- `trait Vfs: Send + Sync` — `list`, `stat`, `open → Box<dyn ByteSource>`; один экземпляр привязан к корню источника и его учётным данным.
- `trait ByteSource: Send + Sync` — `size()` (фиксируется при открытии) и `read_at(&self, offset, buf) → usize` (короткое чтение разрешено, `0` — только при `offset >= size` или пустом буфере). Для потоковых потребителей есть `SourceReader` (`Read + Seek`).
- `VfsPath` — UTF-8, `/`, всегда от корня, без `..`: выйти за корень источника нельзя по построению. Ограничения конкретной платформы (Windows, SMB) проверяет бэкенд → `ErrorKind::InvalidPath`.
- Ошибки — `VfsError` с протоколо-независимым `ErrorKind` (`NotFound`, `PermissionDenied`, `NotADirectory`, `IsADirectory`, `AuthenticationFailed`, `Unavailable`, `TimedOut`…), `non_exhaustive`.
- Сетевые бэкенды внутри держат свой рантайм или пул соединений и блокируют вызывающий поток; read-ahead и prefetch (02 §4) реализуются внутри `ByteSource` бэкенда.
- Время изменения — Unix-миллисекунды `i64`, как в `pa-model`.
- Модуль `pa_vfs::contract` — общий контракт-тест-сьют и фикстура; макрос `vfs_contract_tests!` даёт по `#[test]` на кейс. Каждый бэкенд обязан его проходить (NET-001, CI-012).

Не входит: запись и удаление файлов (не нужны плееру; появятся отдельной задачей вместе с офлайн-загрузками, если понадобятся), watch-уведомления (LIB-005), отмена долгих операций (появится вместе с первым сетевым бэкендом как таймауты бэкенда).

### Последствия

- Хорошо: адаптеры FFmpeg/mpv/Media3 — тонкие; один `ByteSource` безопасно делят потоки; `pa-vfs` без зависимостей; `dyn Vfs` в менеджере источников.
- Плохо (цена решения): async-бэкенды (WebDAV, SFTP) делают `block_on` внутри и не должны вызываться с потока tokio-рантайма; прокси (NET-007) обязан использовать `spawn_blocking`. Поток на одно блокирующее чтение — допустимо для числа одновременных воспроизведений и сканов на клиенте.
- Нейтрально: если появится массовый async-потребитель, поверх синхронного трейта можно добавить async-обёртку без изменения бэкендов.

### Как проверяем соблюдение

Контракт-тесты `pa_vfs::contract` в каждом бэкенде; CI-012 запускает их против реальных серверов; `pa-vfs` тестируется на Linux, Windows и macOS (`rust.yml`, job `test-os`).

## Плюсы и минусы вариантов

### Вариант 1: async

- Плюс: естественно для reqwest и russh, нет блокировки потоков.
- Минус: синхронные колбэки плееров потребуют `block_on` на каждое чтение; `async fn` в трейтах не объектно-безопасен без `async-trait` (бокс на каждый вызов); C-бэкенды всё равно блокирующие.

### Вариант 2: `Read + Seek`

- Плюс: привычный std-интерфейс.
- Минус: курсор → `&mut self` и мьютекс для параллельного чтения; лишние seek-запросы по сети.
