# ADR-0030: LAN-синхронизация — WebSocket поверх TLS 1.3, привязанного к ключам сопряжения, и хаб по классу устройства

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `SYNC-006`, `SYNC-002`, `SYNC-005`, `SYNC-008`, `NET-009`, `SYNC-012`, [ADR-0004](0004-no-project-servers-local-sync.md), [ADR-0019](0019-lan-discovery-mdns.md), [ADR-NNNN (сопряжение)](0026-device-family-pairing.md), `docs/api/sync-protocol.md` §10

## Контекст и проблема

Требование владельца — мгновенное продолжение на другом устройстве без серверов проекта (ADR-0004). Сервер пользователя есть не у всех, поэтому устройства в одной LAN должны синхронизироваться напрямую: найти друг друга, выбрать хаб, шифровать канал и проверять, что на другом конце член семьи. Протокол (`SYNC-002`) и сопряжение (`SYNC-005`) уже есть; `auth` доказывает владение ключом устройства, но сам канал не шифрует и не защищает от активного посредника. Критерий задачи: три устройства в LAN сходятся, при выключении хаба новый выбирается меньше чем за 10 с.

## Факторы решения

- Без серверов проекта и без общего центра доверия.
- Только pure-Rust зависимости, уже одобренные `deny.toml` (в частности, один `sha2` — `deny-multiple-versions`).
- Выключенный хаб (питание, Wi-Fi) не шлёт FIN — нужно своё обнаружение обрыва.
- Устройства могут на мгновение видеть разный набор пиров (mDNS запаздывает).

## Рассмотренные варианты

1. Noise (`snow`) со статическими X25519-ключами из сопряжения.
2. TLS 1.3 с сертификатом из Ed25519-ключа устройства и проверкой по roster.
3. TLS 1.3 с эфемерным сертификатом и привязкой `hello.nonce` к экспортеру TLS (channel binding), `auth` из `SYNC-005` без изменений.

## Решение

Выбран вариант **3**.

- **Канал.** WebSocket (`/sync`) поверх TLS 1.3 (rustls + ring). Каждый узел при старте создаёт эфемерный самоподписанный сертификат (rcgen, не хранится); клиент принимает любой сертификат, но проверяет подпись рукопожатия. `hello.nonce` каждой стороны — не случайное число, а 32 байта экспортера TLS этого соединения (метка `EXPORTER-kinolune-sync-nonce`, контекст `client`/`server`). Получатель сверяет nonce собеседника со своим экспортером, затем проверяет `auth` (подпись Ed25519 из pairing над обоими nonce) по roster. Посредник держит две TLS-сессии с разными экспортерами: пересланные nonce не совпадут, а подписи не сойдутся. Это channel binding в духе RFC 9266; формат `auth` и `pa-pairing` не меняются.
- **Обнаружение.** `_alpha-sync._tcp` (ADR-0019), TXT `dev` — класс устройства, `fp` — отпечаток ключа подписи из сопряжения. Пиры с версией протокола дальше ±1 игнорируются.
- **Выбор хаба.** Каждое устройство само считает хаб — лучший живой кандидат по `(класс, device_id)`: сервер, десктоп, ТВ, телефон; при равенстве — меньший `device_id`. Раунда согласования нет. Обрыв связи с хабом (закрытый сокет или 6 с без кадров при ping каждые 2 с) помечает его мёртвым на 20 с, и устройство подключается к следующему. Новый адрес в анонсе снимает пометку (устройство перезапустилось).
- **Журнал и сходимость.** Каждый узел слушает порт и ведёт журнал всех увиденных операций (`proto::Journal`, новый `log` при каждом старте) — он же журнал хаба. Подключаясь к хабу, устройство отправляет все операции, которые этот журнал ещё не подтвердил, и делает `pull`. Узел пересылает операции и `pb.*` между исходящей и входящими связями; петли гасятся по `op_id` и HLC. Поэтому при временном расхождении выборов (два хаба, цепочка) операции всё равно доходят до всех.
- **Граница.** Узел не владеет медиатекой: он отдаёт события (`Op`, `Acked`, `Playback`, `Takeover`, `HubChanged`, `FamilyChanged`, `Revoked`), а приложение применяет их через `Replica` и `pa_library`. Код — `pa-sync`, модуль `lan` за фичей `lan` (ядро без async-рантайма остаётся без него).

**Не входит:** сохранение журнала узла на диск (после перезапуска журнал пуст, недостающее досылают другие), компактизация, подключение к хабу на сервере пользователя (`SYNC-008`, отдельный канал с pinning из `SRV-004`), обвязка FFI/Flutter, `MulticastLock` на Android (`NET-020`), замер «пауза на A → баннер на B» (`SYNC-012`).

### Последствия

- Хорошо: новых криптозависимостей нет — rustls, ring, rcgen, tokio-tungstenite уже в workspace; `pa-pairing` не меняется.
- Хорошо: смена хаба после закрытия сокета — около 0,2 с, после «тихой» пропажи — около 6,3 с (тесты на loopback).
- Плохо: при смене хаба устройство заново отправляет все неподтверждённые новым журналом операции — O(число операций); пока журнал без компактизации, это растёт со временем.
- Плохо: при расхождении выборов возможны два хаба на короткое время — данные доходят через пересылку, но трафик дублируется до схождения.
- Требует работы: FFI для приложений, сохранение журнала, `SYNC-012` (сходимость и задержка), `NET-020` (Android/Apple).

## Плюсы и минусы вариантов

### Вариант 1 — Noise

- Плюс: канал сразу привязан к статическим ключам из сопряжения.
- Минус: `snow` 0.10 тянет `sha2` 0.10, `chacha20poly1305` 0.10 и `curve25519-dalek` 4 — `sha2` запрещено дублировать (`deny.toml`); свой резолвер криптографии — лишний код в чувствительном месте.

### Вариант 2 — TLS с сертификатом из ключа устройства

- Плюс: стандартная взаимная аутентификация TLS.
- Минус: нужно отдавать приватный ключ Ed25519 из `DeviceIdentity` наружу и собирать из него PKCS#8; взаимный TLS и свой верификатор клиента — больше кода, чем сверка двух nonce.

### Вариант 3 — TLS + экспортер

- Плюс: протокол `SYNC-002` и `pa-pairing` не меняются; привязка канала проверяется одной сверкой строки.
- Минус: идентичность видна только после `hello`/`auth`, а не на уровне TLS; сертификат каждый запуск новый (не используется для доверия, поэтому это не мешает).
