# ADR-0040: Сопряжение приложений по QR и коду в LAN и служба синхронизации в ядре

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `UI-019`, `SYNC-005`, `SYNC-006`, `SYNC-003`, `NET-020`, [ADR-0026](0026-device-family-pairing.md), [ADR-0030](0030-lan-sync-transport.md), [ADR-0019](0019-lan-discovery-mdns.md), [ADR-0037](0037-platform-secret-stores.md)

## Контекст и проблема

Сопряжение (`pa-pairing`, ADR-0026) и LAN-транспорт (`LanNode`, ADR-0030) были в ядре, но приложение ими не пользовалось: pairing работал только с сервером пользователя (`/api/v1/pair`), прогресс писался с `LocalOnly` и в outbox не попадал. Цель UI-019 в этом PR — «мгновенное продолжение» между двумя приложениями в одной LAN без сервера: связать их по QR или 6-значному коду, затем синхронизировать прогресс, «Продолжить просмотр» и «просмотрено».

Нужно решить: как приглашающее приложение принимает pairing без сервера, как присоединяющийся находит его по одному коду, где живёт логика «идентичность + семья + узел + outbox», чем рисовать и сканировать QR в Flutter.

## Факторы решения

- Без серверов проекта (ADR-0004); pairing и sync только в LAN.
- Не менять протокол `pa-pairing` и формат QR из ADR-0026.
- Логику проверять в Rust-тестах без Flutter, FFI — тонкий.
- Лицензии ADR-0005; на Android — без Google Play Services/ML Kit (F-Droid, сборка `full`).
- Работает на ТВ и десктопе без камеры.

## Рассмотренные варианты

1. Транспорт pairing — отдельный слушатель на время приглашения (`PairHost`): WebSocket `/pair` поверх TLS 1.3 с эфемерным сертификатом, анонс `_alpha-pair._tcp` для поиска по коду.
2. Маршрут `/pair` на порту `LanNode`.
3. Поиск приглашающего по коду через широковещание UDP своего формата.

Для сканера QR: `flutter_zxing` (zxing-cpp, MIT/Apache-2.0), `mobile_scanner` (ML Kit), `camera` + чистый Dart-декодер.

## Решение

Выбран вариант **1** и `flutter_zxing`.

- **`pa_sync::lan::pair`.** `PairHost` слушает свой порт, пока открыто приглашение, и принимает по одной попытке за раз (SPAKE2 даёт одну догадку на попытку, `Invitation` считает 5 попыток и 5 минут). TLS не аутентифицирует: присоединяющийся принимает любой сертификат, стороны подтверждает SPAKE2 по коду и ключ приглашающего из QR (`k=`). `join` — сторона присоединяющегося. Формат кадров — `PairMessage` без изменений. У приглашающего ещё нет `LanNode` (узел требует семью), поэтому вариант 2 потребовал бы узел до сопряжения.
- **Поиск по коду.** Новый тип DNS-SD `_alpha-pair._tcp` (`ServiceKind::Pairing`), TXT `id`, `k` (отпечаток ключа подписи), `name`; анонс живёт, пока открыто приглашение. QR несёт `a=host:port` (адрес маршрута по умолчанию) — по QR mDNS не нужен.
- **`pa_sync::lan::service::SyncService`.** Одна служба на приложение: идентичность устройства (создаётся при первом запуске, id `k<uuid v7>`, ключи в `SecretStore`), семья (`roster.json` в каталоге данных, ключ семьи в `SecretStore`), приглашение/присоединение/отвязка, `LanNode` с mDNS и список устройств с признаком «в сети» (связь или виден в mDNS). Свой маленький tokio-runtime (2 потока), блокирующий API — удобно для FFI и тестов. Медиатека подключается через трейт `SyncLibrary` (`enable`, `pending`, `ack`, `apply`), служба отдаёт `ServiceEvent`.
- **Семья при pairing.** Приглашение основывает семью, если её нет. Присоединиться можно, только если у устройства нет других участников (иначе `already_paired`); семья из одного себя (после показа кода) забывается. Сливать две семьи — не входит. После pairing и отзыва узел перезапускается с сохранённой семьёй на том же порту; когда участников не осталось, узел останавливается.
- **Медиатека.** `pa-catalog` пишет прогресс через `Replica` (`ProgressSink`), когда sync включён (`Catalog::enable_sync`), — операция попадает в `sync_outbox` в той же транзакции. Входящие операции — `Catalog::apply_remote` (`Replica::receive_into`, затем LWW по `updated_at_ms` в `progress`). Пока устройство одно, sync выключен и outbox не растёт.
- **Outbox на хабе.** Операции, которые хаб публикует сам, никто не подтверждает. `outbox::compact` оставляет по одной (новейшей) операции на LWW-регистр (`OpBody::register`), так что outbox ограничен числом изменённых элементов; при каждом старте узла он публикуется заново (получатели отбрасывают дубликаты).
- **FFI и приложение.** `pa-frb::api::sync::CoreSync` (поверх `CoreLibrary`, хранилище секретов из `secrets_open_*`), `CoreLibrary.save_progress` сразу будит отправку. В приложении — `DeviceSync` (`CoreDeviceSync`, `FakeDeviceSync` для демо и тестов), экран «Настройки → Устройства», запуск sync при старте, обновление медиатеки по `libraryChanged`. Хук для SYNC-003: события `playback`/`takeover` (`AppServices.playbackElsewhere`), баннер не делается.
- **QR.** Рисуем сами по матрице `qr` (BSD-3, чистый Dart). Сканер — `flutter_zxing` только на телефонах Android/iOS; на десктопе и ТВ — показ QR и ввод кода. `mobile_scanner` отклонён: на Android и в bundled-, и в unbundled-варианте — ML Kit/Play Services.
- **Android.** `MulticastLock` держит `MainActivity` (канал `app.kinolune/device`), пока работает приложение с ядром; разрешения `CHANGE_WIFI_MULTICAST_STATE`, `ACCESS_WIFI_STATE`, `CAMERA` (камера `required="false"`, чтобы не терять ТВ).

**Не входит:** перенос пароля SMB с телефона на ТВ (исходный критерий UI-019 в ROADMAP), баннер «продолжить здесь» (SYNC-003), слияние двух семей, отзыв, который доходит до отозванного устройства, если оно было последним участником, сохранение журнала узла.

### Последствия

- Хорошо: два приложения связываются и синхронизируются без сервера; та же служба годится для ТВ и десктопа; протокол pairing и формат QR не менялись.
- Хорошо: новых Rust-зависимостей нет (rustls, rcgen, tokio-tungstenite, mdns-sd уже были); `pa-frb` теперь тянет фичу `lan` `pa-sync` и `pa-discovery` (mdns-sd) на всех платформах.
- Плохо: `flutter_zxing` собирает zxing-cpp (C++) через CMake/NDK — дольше сборка APK и Linux; на Linux плагин не используется, но собирается.
- Плохо: `MulticastLock` держится всё время работы приложения на Android (батарея); тоньше — в `NET-020`.
- Плохо: при отзыве последнего участника отозванное устройство об этом не узнаёт и показывает его «не в сети», пока его не отвяжут вручную.

### Как проверяем соблюдение

- `core/crates/pa-sync/tests/service.rs`: pairing по QR (и неверный код), по введённому коду через mDNS на loopback, прогресс и «просмотрено» в обе стороны, outbox очищается, отвязка.
- `core/crates/pa-catalog/tests/sync.rs`: два `Catalog` с одинаковыми файлами — позиция с одного попадает в «Продолжить просмотр» другого, «просмотрено» — обратно.
- `clients/flutter/packages/pa_core/test/sync_test.dart`: то же через FRB из Dart.
- `clients/flutter/app/test/devices_test.dart`, `l10n_layout_test.dart`, `tool/screenshots_test.dart`: экран «Устройства» на ru/en-XA без переполнений.
