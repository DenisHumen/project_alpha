# ADR-0002: UI на Flutter для шести платформ, SwiftUI для tvOS

- **Статус:** Принят
- **Дата:** 2026-11-13
- **Решают:** владелец проекта
- **Связано:** `UI-001`, `TV-001`…, `docs/STRATEGY.md` §3, `docs/research/02` §1, `docs/research/01`

## Контекст и проблема

Нужен интерфейс уровня Infuse на Android, Android TV, iOS/iPadOS, macOS, Windows, Linux и Apple TV. Команда — один человек и AI-агенты, поэтому шесть нативных UI нереальны. При этом Apple TV — ключевая платформа для «гостиной», и её UX (фокус, параллакс, Top Shelf) должен быть нативным.

## Факторы решения

- Официальная и стабильная поддержка всех трёх десктопов, включая Linux, и обеих мобильных ОС.
- Поддержка Android TV (D-pad, фокус).
- Качество Apple TV-клиента: нативный фокус-движок, Top Shelf, AVKit, будущий Liquid Glass.
- Объём кода, который агенты пишут уверенно.
- Видео не должно идти через UI-фреймворк (ADR-0003) — фреймворк рисует только экраны и оверлеи.

## Рассмотренные варианты

1. **Flutter** на шести платформах + **SwiftUI** для tvOS.
2. Flutter везде, tvOS через сторонний embedder Flutter.
3. Kotlin Multiplatform + Compose Multiplatform (+ SwiftUI для tvOS).
4. Полностью нативные UI (SwiftUI, Compose, WinUI, GTK).
5. React Native / веб-стек (Tauri, Electron).

## Решение

Выбран вариант **1**.

- **Flutter** — одно приложение `clients/flutter/` для Android, Android TV, iOS, iPadOS, macOS, Windows и Linux. TV-режим Android — отдельный набор экранов в `lib/tv/` с собственным фокус-движком (`TV-002`).
- **SwiftUI** — отдельное приложение для tvOS в `clients/apple/TVApp/`. Ядро подключается через UniFFI-пакет (ADR-0001). В будущем оно может стать основой «Apple-стиля» для iOS и macOS, но это отдельное решение и отдельный ADR.
- Оба UI используют общие дизайн-токены из `design/` (W3C DTCG → Style Dictionary), чтобы выглядеть единообразно.
- State management во Flutter выбирается задачей `UI-001` (рекомендация — Riverpod) и, при споре, отдельным ADR.

### Последствия

- Хорошо: одна кодовая база UI на семь из восьми целей (включая iPadOS); официальная поддержка Linux-десктопа; Dart и Flutter хорошо знакомы агентам.
- Плохо: на tvOS — вторая реализация экранов; на Apple нативный вид (Liquid Glass) во Flutter только эмулируется; HDR и AFR через Flutter `Texture` невозможны, поэтому плеер — отдельная нативная поверхность (ADR-0003).
- Требует работы: каркас `UI-001`, TV-фокус `TV-002`, tvOS-приложение `TV-0xx`; паритет экранов Flutter ↔ SwiftUI отслеживается в ROADMAP.

## Плюсы и минусы вариантов

### Flutter со сторонним tvOS-embedder

- Плюс: одна кодовая база UI.
- Минус: зависимость от одного мейнтейнера форка и отставание от версий Flutter; нет нативного фокуса и Top Shelf. Риск слишком велик для главной «гостиной» платформы.

### KMP + Compose Multiplatform

- Плюс: лучшая TV-история на Android (Compose for TV), нативный Media3.
- Минус: десктоп на JVM (вес, старт, встраивание видео); tvOS тоже не поддерживается; меньше готовых решений для Linux.

### Полностью нативные UI

- Плюс: лучший нативный вид и производительность.
- Минус: 4–5 реализаций каждого экрана — непосильно для команды.

### React Native / Tauri / Electron

- Плюс: веб-навыки.
- Минус: слабый Linux у RN, тяжёлый Electron, нет tvOS (кроме форков), сложное встраивание нативного видео.
