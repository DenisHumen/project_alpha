# ADR-NNNN: Локальный индекс названий — свой индекс в памяти в `pa-recognition`, синонимы anime-offline-database в бандле

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** META-007 (реализация), META-008 (бандл anime-offline-database), META-009 (кэш TMDB), META-010/011 (Shikimori, дамп названий AniDB), META-014 (скорер); ADR-0018; `docs/research/03-metadata-recognition.md` §4.2 [4], §4.3

## Контекст и проблема

Этап [4] конвейера (03 §4.2) — генерация кандидатов. Большая часть кандидатов должна находиться без внешних запросов: без лимитов провайдеров, приватно и офлайн. Особенно это нужно для аниме (фансаб-имена в ромадзи, сезоны как отдельные записи AniDB) и русских релизов (кириллица и транслит в любой схеме). Нужно решить, чем искать (готовый поисковый движок или свой индекс), где он живёт и откуда берутся названия.

## Факторы решения

- Ядро sans-IO и детерминировано: один и тот же запрос даёт тот же список (eval на корпусе побайтно).
- Работает на всех платформах ядра, включая Android и iOS, без файловых блокировок и фоновых потоков.
- Объём: ~40 тыс. записей anime-offline-database, ~220 тыс. названий с синонимами плюс горячий кэш TMDB — это небольшой объём для памяти.
- Нормализация специфична для домена (транслит, ромадзи, квалификаторы сезонов); её надо применять одинаково к индексу и к запросу.
- Минимум зависимостей, лицензии по ADR-0005.

## Рассмотренные варианты

1. Свой индекс в памяти в `pa-recognition`: точные карты ключей + инвертированный индекс токенов (IDF) + триграммы.
2. `tantivy` (BM25, fuzzy-запросы, индекс на диске).
3. SQLite FTS5 в `pa-library`.

## Решение

Выбран вариант **1**.

- `pa_recognition::title`: `normalize` (ключи plain / loose / base), `translit` (ГОСТ 7.79-2000 Б и бытовая схема, обратно — для запросов), `index` (`TitleIndex`, `TitleRecord`, `TitleQuery::from_parse`, ранжированные `Candidate`), `anime` (записи из anime-offline-database). Транслит и варианты ромадзи сводятся в одно «свободное» латинское пространство, поэтому матчинг работает в обе стороны без перебора схем.
- Источник аниме-названий — бандл META-008: в производную ODbL-базу добавлены синонимы (`synonyms`) латиницей, кириллицей, каной и иероглифами; остальные письменности отбрасываются. Бандл вырос примерно с 6 до 15 МБ (несжатый JSONL).
- Кэш TMDB подключается через `pa_metadata::tmdb::titles::title_record` (оригинальное и локализованное название, переводы, альтернативные названия). Shikimori и дамп названий AniDB (META-010/011) подключаются так же — записями `TitleRecord`.
- Оценка — `pa-eval candidates`: recall@k на корпусе без внешних запросов.
- Не входит: сохранение индекса на диск (сейчас он строится при запуске, ~1,5 с на сервере сборки для полного бандла), скоринг и пороги (META-014/016/018).

### Последствия

- Хорошо: без новых тяжёлых зависимостей (только `unicode-normalization`), детерминизм, нормализация одна для индекса и запроса, R@10 ≥ 99 % на корпусе v0.
- Плохо: индекс держится в памяти (десятки МБ для полного бандла); построение при каждом запуске; бандл anime-offline-database стал больше.
- Требует работы: сериализация готового индекса или ленивое построение на слабых устройствах; перезапись офлайн-каталога фильмов и сериалов из настоящего кэша TMDB, когда появится ключ (DEC-008).

## Плюсы и минусы вариантов

### Вариант 2 — tantivy

- Плюс: зрелый BM25, fuzzy, индекс на диске.
- Минус: крупная зависимость с потоками и mmap, отдельная сборка под мобильные платформы; доменную нормализацию всё равно пришлось бы писать самим; детерминизм ранжирования сложнее контролировать.

### Вариант 3 — SQLite FTS5

- Плюс: SQLite уже есть в `pa-library`.
- Минус: индекс оказывается в слое медиатеки, а не в sans-IO ядре распознавания; FTS5 не делает нечёткий поиск по триграммам с нашей нормализацией без собственного токенизатора; eval пришлось бы гонять через БД.
