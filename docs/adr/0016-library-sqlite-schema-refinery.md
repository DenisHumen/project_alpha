# ADR-0016: Хранить медиатеку в SQLite одной схемой с миграциями refinery

- **Статус:** Принят
- **Дата:** 2026-11-13
- **Решают:** мейнтейнер (решения делегированы владельцем, ADR-0011)
- **Связано:** `LIB-001`, `LIB-002`, `LIB-015`, `CORE-005`, `R01-LIB`; [03 §5](../research/03-metadata-recognition.md#5-модель-данных), [04 §1.3–1.5](../research/04-backend-architecture-billing.md); [docs/dev/db.md](../dev/db.md)

## Контекст и проблема

Медиатека нужна и клиенту без сервера (режим A), и медиасерверу (режим B), и NAS-ОС, где bootc не откатывает `/var` — значит, схема должна мигрировать предсказуемо и оставаться читаемой предыдущей версией. Задачи идут параллельно в нескольких ветках, поэтому порядок миграций не должен зависеть от порядка слияния. Релиз 0.1 уже работает на временной Dart-базе `pa_library` v0, которую Rust-ядро заменит.

## Факторы решения

- Одна схема и один код для всех платформ и сервера.
- Атомарность: сбой при обновлении не оставляет полусхему.
- Параллельные ветки добавляют миграции без перенумерации.
- Только разрешённые лицензии (ADR-0005, cargo-deny).
- Целостность данных проверяется самой базой, а не только кодом.

## Рассмотренные варианты

1. `rusqlite` + `refinery`, SQL-файлы с меткой времени, `STRICT`-таблицы.
2. `rusqlite` + свой мини-раннер на `PRAGMA user_version`.
3. `sqlx` (async, миграции `sqlx migrate`).
4. ORM (`diesel`, `sea-orm`).

## Решение

Выбран вариант **1**: зрелый раннер с контролем контрольных сумм, без async-рантайма и ORM, лицензии MIT/Apache-2.0, SQLite собирается из исходников (public domain).

- Крейт `pa-library` владеет схемой; миграции — `core/crates/pa-library/migrations/YYYYMMDDHHMM_<ID>_<slug>.sql`, встроены в бинарь (`include_str!`), версия refinery = метка времени (фича `int8-versions`).
- Все ожидающие миграции — одной транзакцией (`set_grouped(true)`); изменённая применённая миграция — ошибка.
- База от более новой сборки открывается (правило expand→contract, `LIB-002`); неизвестная старая версия или пропущенная миграция — ошибка.
- `STRICT`-таблицы, внешние ключи с явными `ON DELETE`, `CHECK` на закрытых перечислениях из `pa-model`, slug-проверка на открытых наборах, `json_valid()` на JSON-столбцах; WAL, `foreign_keys`, `synchronous = NORMAL`, `busy_timeout`.
- Локальные `INTEGER PRIMARY KEY` не синхронизируются; синхронизация — по `media_key` и `profiles.sync_id`.
- База v0 (Dart) не мигрирует на месте: Rust-база — отдельный файл, `migrate` отказывается трогать v0 (`ForeignDatabase`), перенос — задача импорта `LIB-015`.
- Postgres не поддерживаем (04 §1.5); слой запросов не абстрагируем, пока нет запроса.

### Последствия

- Хорошо: одна схема для клиента и сервера; целостность проверяет SQLite; параллельные ветки не конфликтуют номерами миграций.
- Плохо: `CHECK` на закрытом перечислении меняется только пересборкой таблицы; refinery ограничивает имя миграции `\w`, поэтому имя для refinery выводится из имени файла.
- Требует работы: `LIB-002` (фикстуры прошлых версий), `LIB-015` (импорт v0).

### Как проверяем соблюдение

Тесты `pa-library`: миграция с нуля, FK указывают на уникальные ключи и проиндексированы, каскады, каждый вариант перечислений `pa-model` проходит `CHECK`, каталог миграций совпадает со списком, каждая таблица описана в `docs/dev/db.md`, отказ на v0, на изменённой и на неизвестной миграции.
