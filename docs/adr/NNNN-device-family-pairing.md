# ADR-NNNN: Семья устройств: ключи Ed25519/X25519, pairing через SPAKE2, подписанный trust store

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** `SYNC-005`, `SYNC-006`, `SYNC-008`, `SYNC-010`, `SRV-003`, `SRV-004`, [ADR-0004](0004-no-project-servers-local-sync.md), `docs/api/sync-protocol.md`

## Контекст и проблема

Аккаунта проекта нет (ADR-0004), поэтому устройства пользователя доверяют друг другу только после локального сопряжения. Нужно: связать новое устройство по QR или 6-значному коду в LAN без облака, вести список устройств, отзывать устройство (отозванное больше не подключается — критерий `SYNC-005`), менять общий ключ семьи после отзыва. Хаб на сервере (`SYNC-008`) должен отвечать неизвестным и отозванным устройствам `unauthorized`. Тот же механизм нужен P2P в LAN (`SYNC-006`) и E2E-контейнеру паролей (`SYNC-010`).

## Факторы решения

- Без серверов проекта и без аккаунтов; работает офлайн в LAN.
- 6 цифр — слабый секрет: перехват кадров не должен давать офлайн-перебор.
- Нет «главного» устройства: любое может пригласить и отозвать; сервер — равноправный член.
- Только проверенная чистая Rust-криптография под MIT/Apache/BSD, без OpenSSL (ADR-0005, `deny.toml`).
- Приватные ключи — только в `pa-secrets` (CORE-007), не в БД и не в логах.

## Рассмотренные варианты

1. **SPAKE2 по коду + подписанные записи устройств (новый крейт `pa-pairing`).**
2. Обмен ключами с кодом как HMAC-ключом.
3. Сравнение SAS (как Bluetooth Numeric Comparison): оба экрана показывают число, пользователь подтверждает.
4. Только TLS-сертификаты сервера с ручным подтверждением отпечатка (TOFU).

## Решение

Выбран вариант **1**.

- **Ключи устройства** (`DeviceIdentity`): Ed25519 (`ed25519-dalek`) для подписей и X25519 (`x25519-dalek`) для доставки ключа семьи. Хранятся в `SecretStore` (`pairing.identity`). На сервере — `EncryptedFileStore` в каталоге данных (у headless-сервера нет keychain).
- **Pairing** (`pa_pairing::pair`, sans-IO): SPAKE2 (`spake2` из RustCrypto PAKEs, группа Ed25519) с кодом как паролем. Пассивный слушатель ничего не узнаёт, активный атакующий получает одну попытку угадать на сессию; приглашение — 5 попыток за 5 минут, после успеха гасится. Из ключа SPAKE2 и хэша транскрипта (HKDF-SHA256) получаются два ключа ChaCha20-Poly1305: `pair.intro` (устройство, ключи, подпись транскрипта) и `pair.welcome` (roster, ключ семьи, подпись транскрипта). QR-код (`projectalpha://pair?v=1&c=…&k=…&a=…`) несёт 128-битный код и ключ пригласившего, присоединяющийся сверяет его.
- **Trust store** (`Roster`): записи устройств подписаны тем, кто их принял (sponsor); основатель подписывает себя сам, id семьи — хэш его ключа. Отзыв — подписанная запись о ключе (не только об id). Roster не секретный: JSON рядом с данными (`devices.json` на сервере). Любое устройство проверяет его само и сливает (`merge`) с roster другого члена: отзыв не отменяется, новые записи от уже отозванного ключа не принимаются.
- **Ключ семьи** (`FamilyKey`, эпоха + 256 бит, `pairing.family_key`): при отзыве ротируется; каждому оставшемуся члену его запечатывают в `KeyEnvelope` (статический X25519 → HKDF-SHA256 → ChaCha20-Poly1305, подпись отправителя). Два одновременных отзыва дают два ключа одной эпохи — все оставляют ключ с бо́льшим хэшем, и семья сходится.
- **Аутентификация соединения синхронизации:** `hello.nonce` + сообщение `auth` (подпись Ed25519 обоих id и обоих nonce), взаимная. Хаб отвечает `error{unauthorized}` неизвестному, отозванному устройству и устройству без доказательства; отозванное во время работы отключается сразу. После рукопожатия член семьи получает `family` (roster и свой конверт ключа); `family` от члена хаб сливает к себе — так отзыв, сделанный на телефоне, доходит до сервера.
- **Сервер:** при первом запуске основывает семью; приглашение и управление — loopback-API (`POST /api/v1/pair/invite`, `GET /api/v1/devices`, `DELETE /api/v1/devices/{id}`) до появления учётных записей (`SRV-003`); pairing — WebSocket `/api/v1/pair`. `sync.require_pairing = true` по умолчанию.

**Не входит:** шифрование канала (TLS сервера — `SRV-004`, Noise для P2P — `SYNC-006`; до них `auth` доказывает, кто на другом конце, но не защищает от активного MITM внутри канала), присоединение сервера к уже существующей семье телефона (сейчас сервер всегда основатель; нужен клиентский путь в `SRV-003`/UI), UI списка устройств.

### Последствия

- Хорошо: сопряжение без облака и без центра; слабый код безопасен против офлайн-перебора; список и отзыв проверяемы на любом устройстве; тот же ключ семьи пригоден для `SYNC-010`.
- Плохо: `spake2` взят пре-релизной версией `=0.5.0-pre.0` — она единственная собрана на тех же `curve25519-dalek` 5 / `sha2` 0.11, что и остальные крейты (0.4 тянет вторые копии); сам `spake2` отдельно не аудирован (аудирован `curve25519-dalek`, на котором он построен). Перейти на 0.5.0 при выходе.
- Плохо: украденное устройство может успеть принять «свои» устройства до того, как отзыв дойдёт до остальных; после отзыва такие записи видны в списке и отзываются вручную.
- Требует работы: клиентский UI (QR-сканер, ввод кода, список устройств), транспорт pairing в P2P (`SYNC-006`), TLS (`SRV-004`).

### Как проверяем соблюдение

- `server/tests/pairing.rs`: отозванное устройство отключается и больше не подключается, в том числе после перезапуска; неверный код тратит попытку; чужой ключ под чужим id получает `unauthorized`.
- Модульные тесты `pa-pairing`: подделка roster, слияние, конверты ключа, сходимость одновременных ротаций.
- `cargo deny check`: только лицензии ADR-0005, без OpenSSL.

## Плюсы и минусы вариантов

### Код как HMAC-ключ

- Плюс: проще.
- Минус: записав обмен, атакующий перебирает 10⁶ кодов офлайн за доли секунды.

### SAS-сравнение

- Плюс: безопасно с 6 цифрами.
- Минус: нужны два экрана рядом и подтверждение на обоих; у headless-сервера экрана нет.

### TOFU-сертификаты

- Плюс: стандартный TLS.
- Минус: нет общего ключа семьи и отзыва между клиентами; доверие только к серверу, P2P не покрывается.
