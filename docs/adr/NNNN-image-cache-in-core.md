# ADR-NNNN: Кэш изображений в ядре: размеры через URL провайдера, декодирование во Flutter

- **Статус:** Предложен
- **Дата:** 2026-11-14
- **Решают:** владелец проекта (мейнтейнер); участники обсуждения — по PR
- **Связано:** LIB-013, META-027 (таблица `artwork`), CORE-006 (`PlatformDirs::cache`), ADR-0018 (HTTPS-стек `pa-metadata`), ADR-0032 (медиатека на Rust-ядре)

## Контекст и проблема

Постеры, фоны и кадры эпизодов приходят из TMDB, AniList и Shikimori ссылками (`CoreItem.poster_url`/`backdrop_url`). До LIB-013 приложение грузило их `Image.network`: без дискового кэша, без работы офлайн, каждый раз в полном размере (`w500` для постера в сетке шириной 150 px) и с декодированием в полном размере. Нужен дисковый кэш с лимитом, работающий без сети, и по условиям TMDB — только локальный, без раздачи другим.

## Факторы решения

- Одна реализация на все платформы (Linux, Android, Apple, Windows), без OpenSSL.
- Лимит размера соблюдается и переживает перезапуск.
- Сетка из 10 000 постеров без пропусков кадров из-за декодирования.
- Минимум новых зависимостей (cargo-deny, размер бинарника).
- Условия TMDB: кэш только у пользователя, не дольше шести месяцев.

## Рассмотренные варианты

1. Кэш в ядре (`pa-imagecache`) на уже имеющемся `ureq` + rustls, размеры — через URL провайдера, декодирование и масштабирование — во Flutter (`ResizeImage`).
2. Кэш в ядре с собственным ресайзом (крейт `image`): ядро хранит готовые варианты под плотности.
3. Кэш на стороне Dart (`flutter_cache_manager` / `cached_network_image`).

## Решение

Выбран вариант **1**: сеть и диск — в ядре, как остальной ввод-вывод; декодирование — там, где картинку рисуют.

- Крейт `core/crates/pa-imagecache`: `ImageCache::get(url, width)` возвращает локальный путь. Файлы `<sha256(url)[..32]>-<время загрузки>.<ext>` в `PlatformDirs::cache/artwork`; последний доступ — mtime файла (обновляется не чаще раза в 10 минут), поэтому порядок LRU переживает перезапуск без отдельной базы.
- Лимит (`max_bytes`, по умолчанию 256 МиБ) проверяется после каждой записи; при превышении удаляются самые давние по доступу файлы до 90 % лимита.
- Размеры: для TMDB берётся наименьшая ширина из набора провайдера, покрывающая пиксели на экране, но не больше сохранённой (`w500` постер → `w92…w500`, `w1280` фон → `w300/w780/w1280`). Другие провайдеры — как есть.
- Офлайн: при ошибке сети отдаётся любой закэшированный размер того же изображения; `cached()` вообще не ходит в сеть (синхронный вызов для первого кадра).
- Срок жизни — 180 дней от загрузки (условия TMDB); устаревший файл перезагружается, а без сети — удаляется. Файлы никому не раздаются.
- Локальные постеры рядом с медиа (`poster.jpg`, LIB-007) не копируются: путь отдаётся как есть.
- Flutter: `CachedArtworkImage` (ImageProvider) берёт путь у ядра и декодирует файл через `ResizeImage` в ширину на экране (кратную 64 физ. пикселям) на потоках движка, а не на UI-потоке.

Не входит: собственный ресайз и перекодирование в ядре, AVIF-декодер (Flutter AVIF не декодирует; кэш AVIF хранит, но провайдеры его не отдают), настройка лимита в UI.

### Последствия

- Хорошо: без новых внешних зависимостей (только `sha2`, `ureq` уже в дереве); офлайн-сетка работает; трафик сетки ниже в 2–5 раз.
- Плохо: AniList/Shikimori и локальные постеры хранятся/читаются в исходном размере (декодирование всё равно в размер экрана). Порядок LRU приблизителен в пределах 10 минут.
- Нейтрально: на tvOS кэш лежит в `Library/Caches` и может быть очищен системой — кэш просто начинается пустым.

## Плюсы и минусы вариантов (опц.)

### Вариант 2

- Плюс: варианты под плотности и для любых провайдеров.
- Минус: крейт `image` с декодерами — заметный рост бинарника на всех платформах; AVIF требует C-библиотеку (dav1d); двойное декодирование (ядро + Flutter).

### Вариант 3

- Плюс: готовые пакеты.
- Минус: только для Flutter (нативные плееры и tvOS не получают кэш), отдельный HTTP-стек на Dart, `sqflite` для индекса.
