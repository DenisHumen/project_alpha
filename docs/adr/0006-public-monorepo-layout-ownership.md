# ADR-0006: Один публичный монорепо, раскладка каталогов и владение ими

- **Статус:** Принят (включает решение владельца `DEC-001`)
- **Дата:** 2026-11-13
- **Решают:** владелец проекта
- **Связано:** `DEC-001`, `REPO-001`, `REPO-011`, `META-001`, `SITE-001`, `PLAY-001`, `docs/ROADMAP.md` §0.4–0.5, `docs/STRATEGY.md` §7, `docs/research/04` §4.1, `docs/research/02` §3.1

## Контекст и проблема

Исследование 04 предполагало приватный монорепо и отдельный публичный `project_alpha-releases` для сборок, а также облачный каталог `cloud/`. В STRATEGY v2 проект стал открытым и локальным. Кроме того, над задачами одновременно работают десятки AI-агентов и внешние контрибьюторы в своих worktree. Им нужна раскладка, в которой параллельные PR почти не конфликтуют, и ясное правило, кто какой каталог меняет.

Остаются вопросы, которые в ROADMAP §0.4 намечены, но не обоснованы: где живут спайки, исходники и патчи сторонних C-библиотек, сайт, удалённые конфиги и корпус для оценки распознавания (данные со смешанными лицензиями).

## Факторы решения

- Один источник правды: код, документация, задачи, релизы.
- Минимум конфликтов между параллельными PR (горячие файлы, владение каталогами).
- Один Cargo workspace для ядра, сервера и инструментов (общий `Cargo.lock` и кэш).
- Лицензионная чистота продукта (ADR-0005): данные с чужими лицензиями не попадают в сборки.
- Простота для контрибьютора: `git clone` + `just` — и всё собирается.

## Рассмотренные варианты

1. **Один публичный монорепо** с релизами в GitHub Releases этого же репо, плюс отдельный репо только для eval-корпуса.
2. Приватный монорепо + публичный `project_alpha-releases` (исследование 04 §4.6).
3. Полирепо: отдельные репо для ядра, Flutter-клиента, Apple-клиента, сервера, дистрибутива, сайта.
4. Один публичный монорепо **вообще без исключений** (корпус тоже внутри).

## Решение

### Репозиторий и релизы (`DEC-001`, принято владельцем)

- Единственный основной репозиторий — публичный `DenisHumen/project_alpha` (MPL-2.0, ADR-0005).
- Все сборки публикуются в **GitHub Releases этого же репо**. Репо `project_alpha-releases` больше не нужен и удаляется; ссылки на него в документации не используются.
- Видимость переключает задача `REPO-011`.
- Сайт тоже живёт в этом репо (`site/`) и публикуется в GitHub Pages через Actions — отдельный репо для сайта не нужен.

### Раскладка (подтверждает ROADMAP §0.4 с уточнениями)

```
project_alpha/
├── core/crates/          # Rust-ядро: pa-* крейты
├── server/               # медиасервер (axum) + server/web (веб-админка)
├── clients/
│   ├── flutter/          # Flutter-приложение (Android, Android TV, iOS, iPadOS, macOS, Windows, Linux)
│   │   └── packages/     # pa_core (FRB), pa_player_android|apple|desktop
│   ├── android/          # Kotlin: Media3-плеер, MediaSession/Auto, TV-каналы
│   ├── apple/            # Swift: AlphaPlayerKit, TVApp (tvOS), AudioKit, CarPlay
│   └── desktop/          # нативный хост libmpv (Win/Linux/macOS)
├── distro/               # NAS-ОС (bootc, установщик, админка, обновления)
├── design/               # дизайн-токены DTCG, иконки, бренд (Git LFS)
├── packaging/            # flatpak, AUR, winget, MSIX, DMG, F-Droid, Docker, nfpm
├── config/               # публичные подписанные удалённые конфиги (twitch/remote-config.json …)
├── data/                 # встраиваемые открытые данные (anime-mappings) с лицензиями по REUSE
├── third_party/          # скрипты сборки и патчи C-библиотек (ffmpeg, mpv, libass, libsmb2, libnfs)
├── spikes/               # одноразовые прототипы под ADR; в сборки и workspace не входят
├── tools/                # bindings, ffmpeg, recognition-eval (раннер), roadmap, ci, qa
├── tests/                # e2e, тестовые медиа (LFS), фикстуры
├── site/                 # сайт (GitHub Pages)
└── docs/                 # research, adr, api, dev, user, legal, STRATEGY, ROADMAP
```

Каталога `cloud/` нет (ADR-0004). Корневой `Cargo.toml` задаёт `members` глобами (`core/crates/*`, `server`, `tools/*`), поэтому новый крейт корень не трогает; `spikes/` в workspace **не** входит.

### Обоснование отдельных каталогов

- **`clients/flutter/`** — одно Flutter-приложение на семь целей (ADR-0002). Плеерные плагины лежат в `packages/`, чтобы PLAY-полосы не трогали `lib/` UI-полосы. Нативный код плеера (Kotlin, Swift, C++) вынесен в `clients/{android,apple,desktop}/`: его собирают и тестируют своими инструментами (Gradle, SwiftPM, CMake), а tvOS-приложение на SwiftUI (`clients/apple/TVApp/`) использует тот же Swift-код без Flutter.
- **`config/`** — удалённые конфиги и kill-switch без сервера (ADR-0004, `CORE-014`). Файлы подписаны minisign и раздаются через GitHub Pages/raw. Отдельный каталог в корне нужен, потому что его публикует отдельный workflow с отдельным ключом, а правки идут быстрее релизного цикла.
- **`site/`** — в этом же репо, а не отдельно (`DEC-001`): документация, страница «Скачать» и `releases.json` генерируются из тех же исходников, что и релизы, и меняются в одном PR с кодом.
- **`spikes/`** — прототипы для решений (например `spikes/android-player` для ADR-0008). Код спайка не обязан проходить все линтеры и не поддерживается после принятия ADR. Правила: в каждом спайке `README.md` со ссылкой на задачу и ADR; после принятия ADR спайк удаляется отдельным PR (история остаётся в git) или переносится в продуктовый каталог через обычную задачу. Спайки не входят в Cargo workspace, Flutter-сборку и релизы. Владелец каталога `spikes/<name>/` — workstream задачи, создавшей спайк.
- **`third_party/`** — только скрипты сборки, конфигурация и **патчи** к LGPL/BSD C-библиотекам; исходники upstream не вендорятся в git, а скачиваются по зафиксированной версии и контрольной сумме. LGPL требует публиковать точные исходники и патчи (исследование 02 §3.1); вместо отдельного репо `project_alpha-thirdparty`, предложенного там, архивы точных исходников прикладываются к каждому GitHub Release этого репо, а патчи лежат здесь. Отдельный каталог (а не внутри `tools/`) нужен, чтобы REUSE и лицензионные проверки видели чужой код в одном месте.
- **`data/`** — встраиваемые в продукт открытые данные (снапшот anime-lists и т. п.) с лицензиями, совместимыми с продуктом (`LEGAL-003`). Отдельно от кода, потому что у данных свои лицензии и свой цикл обновления.
- **Eval-корпус распознавания — отдельный репо `project_alpha-recognition-eval`** (`META-001`). Это **единственное исключение** из «одного репо». Причины: корпус содержит данные со смешанными и иногда несовместимыми с MPL лицензиями (тест-кейсы guessit/anitomy/Sonarr, RSS-заголовки), объёмные LFS/DVC-файлы и закрытый test-сплит. Ни одна строка корпуса не должна попасть в продукт или в историю основного репо. Раннер (`pa-eval`, `tools/recognition-eval/`) остаётся в монорепо под MPL-2.0 и получает корпус по зафиксированному коммиту (рецепт `just`, не git submodule), чтобы обычный `git clone` не требовал корпуса.

### Владение каталогами и горячие файлы

Таблица владения из ROADMAP §0.4 и правила горячих файлов из §0.5 являются частью этого решения и меняются только вместе с этим ADR (новым ADR, который его заменяет). Дополнения к таблице:

| Workstream | Дополнительно владеет |
|---|---|
| задача-спайк (любой workstream) | `spikes/<name>/` |
| META | репо `project_alpha-recognition-eval` |
| LEGAL | `REUSE.toml` (совместно с REPO по `REPO-002`) |

### Последствия

- Хорошо: один `git clone` для всего; задачи, код, документация, сайт и релизы меняются атомарно в одном PR; владение каталогами позволяет вести много параллельных PR без конфликтов; лицензионно «грязные» данные изолированы.
- Плохо: репо будет большим (нужны Git LFS и sparse checkout для отдельных полос); CI должен фильтровать джобы по путям; контрибьютору eval нужен второй репо.
- Требует работы: `REPO-001` (каркас по этой раскладке, включая `spikes/`, `third_party/`, `data/` с `README.md`), `REPO-011`, CODEOWNERS по таблице владения, `META-001` (отдельный eval-репо), path-фильтры CI.

### Как проверяем соблюдение

- `just roadmap lint` и CODEOWNERS: PR, меняющий чужой каталог, требует ревью владельца.
- CI проверяет, что `spikes/` не упоминается в релизных сборках, а `third_party/` не содержит вендоренных исходников upstream без записи в REUSE.

## Плюсы и минусы вариантов

### Приватный монорепо + публичный releases-репо

- Плюс: можно держать код закрытым.
- Минус: противоречит open source; две истории; нужен GitHub App token для публикации — лишняя сложность.

### Полирепо

- Плюс: маленькие репо, независимые релизы.
- Минус: изменение API ядра требует согласованных PR в 3–5 репо; дрейф версий; агентам сложнее.

### Монорепо без исключений

- Плюс: абсолютно один репо.
- Минус: данные с несовместимыми лицензиями и закрытый test-сплит попадают в публичную историю MPL-репо — их уже нельзя будет удалить из git-истории без переписывания.
