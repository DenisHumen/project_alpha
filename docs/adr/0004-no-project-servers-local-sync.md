# ADR-0004: Без серверов проекта; синхронизация через устройства и хранилища пользователя

- **Статус:** Принят
- **Дата:** 2026-11-13
- **Решают:** владелец проекта (STRATEGY v2)
- **Связано:** `SYNC-001`…, `SRV-…`, `CORE-014`, `DEC-006`, `DEC-008`, `docs/STRATEGY.md` §1–3, §6, §10, `docs/research/04` §1.5–1.8

## Контекст и проблема

Исследование 04 предлагало своё облако (Postgres, аккаунты, entitlement, хаб синхронизации, краудсорс-маппинги), а 06 — облачный Twitch-шлюз и EventSub-webhook. В STRATEGY v2 владелец решил: проект — open source, всё работает **локально**, деньги — добровольные пожертвования. Своё облако противоречит этому: оно стоит денег каждый месяц, требует хранить персональные данные (история просмотров, токены) и создаёт единую точку отказа. При этом «продолжить на другом устройстве с той же секунды» остаётся обязательной функцией.

## Факторы решения

- Ноль постоянных расходов и ноль персональных данных у проекта (GDPR практически не касается проекта).
- Продолжение просмотра между устройствами с точностью ≤ 2 с (критерий M3).
- Работа без интернета в домашней сети.
- Приложение остаётся полезным, если проект перестанет развиваться: нечему «выключиться».
- Режимы A (только приложение), B (свой сервер) и C (Plex/Jellyfin/Emby) равноправны.

## Рассмотренные варианты

1. **Без серверов проекта**: хабом синхронизации служит то, что уже есть у пользователя.
2. Минимальное облако проекта (VPS + Postgres) для аккаунтов и синхронизации.
3. Платформенные облака (CloudKit, Google Drive appdata).
4. Только свой сервер пользователя (режим B) как единственный способ синхронизации.

## Решение

Выбран вариант **1**. У проекта **нет** серверов, через которые проходят данные пользователей. Устройство или сервер пользователя обращаются напрямую к публичным сервисам (TMDB, AniList, Shikimori, MusicBrainz, Twitch и т. п.).

**Схемы синхронизации** (один протокол, разные транспорты):

| Ситуация | Транспорт | Хаб |
|---|---|---|
| Есть свой сервер (режим B) | WebSocket к серверу: heartbeat 5 с + сразу на паузе/перемотке, HLC, офлайн-outbox | сервер пользователя |
| Только приложения, одна LAN | P2P: обнаружение через mDNS, тот же протокол напрямую | любое включённое устройство |
| Только приложения, вне дома | Append-only журнал на устройство в той же SMB/WebDAV-папке (`.project_alpha/state/*.jsonl`), слияние по HLC | хранилище пользователя |
| Удалённый доступ к своему серверу | iroh (QUIC + NAT traversal) с публичными relay n0 или relay пользователя; альтернатива — Tailscale/WireGuard пользователя | сервер пользователя |
| Опционально | Trakt (аккаунт пользователя) — история просмотров | Trakt |

Модель данных: LWW по HLC и `device_id`; «просмотрено» монотонно (снятие — явная операция с более новым HLC); ключ записи `(profile, media_key)`. Ключи медиа: внешний ID (TMDB/TVDB/IMDb + сезон/серия) или `content_fingerprint`; Twitch VOD — `twitch:vod:<id>` (онлайн и скачанный — один ключ). Протокол описывается в `docs/api/sync-protocol.md` (`SYNC-002`).

**Что заменяет облачные функции из исследований:**

- Метаданные — запросы напрямую с устройства или сервера пользователя.
- Маппинги аниме (anime-lists) — снапшот встроен в приложение и обновляется с GitHub.
- Удалённые конфиги и kill-switch (Twitch GQL и др.) — подписанные minisign JSON-файлы в `config/` этого репо, раздаются через GitHub Pages или raw (`CORE-014`).
- Twitch — Device Code Flow с устройства (публичный `client_id`, без секрета); уведомления — EventSub WebSocket или опрос с сервера/приложения.
- Краудсорс «хэш → ID» — отменён; позже возможен как **опциональный** открытый датасет в git.

### Последствия

- Хорошо: нет счетов за облако, нет хранения персональных данных, нет единой точки отказа; синхронизация работает офлайн в LAN; проект проще передать сообществу.
- Плохо: синхронизация вне дома без своего сервера медленнее (через папку, не мгновенно); нет «аккаунта проекта» — профили и устройства связываются локально (сопряжение по QR/коду); нельзя слать push-уведомления от нашего имени (APNs/FCM требуют сервер) — только локальные уведомления и опрос.
- Требует работы: `SYNC-*` (HLC, outbox, P2P, журнал в папке), `SRV-*` (хаб), `CORE-014` (удалённый конфиг), `NET-*` (iroh).

### Как проверяем соблюдение

- Ревью отклоняет любой код, который шлёт данные пользователя на домены проекта. Разрешены только раздача статических файлов (GitHub Releases/Pages, R2 для ISO) и прямые запросы к сторонним сервисам.
- Телеметрия — только opt-in (ROADMAP §0.3 п. 10).

## Открытые вопросы (решает владелец; будут отдельными ADR в статусе «Предложен»)

- **DEC-008 — ключ TMDB в открытом коде.** Рекомендация: встроенный ключ проекта по умолчанию + поле «свой ключ»; окончательно — после письменного ответа TMDB (`LEGAL-001`). Не меняет принцип «без серверов»: запросы в любом случае идут с устройства.
- **DEC-006 — Twitch без логина.** Рекомендация: без логина — избранное локально и публичные данные; полноценные функции — после входа через Device Code Flow (QR на ТВ). Решается по итогам прототипа `TWI-003`. Любой вариант работает без нашего сервера.

## Плюсы и минусы вариантов

### Минимальное облако проекта

- Плюс: мгновенная синхронизация вне дома без своего сервера, push-уведомления.
- Минус: $10–30/мес и рост с аудиторией; хранение персональных данных и токенов; противоречит STRATEGY v2.

### CloudKit / Google Drive appdata

- Плюс: бесплатно и приватно.
- Минус: CloudKit покрывает только Apple; две логики слияния; нет Linux/Windows.

### Только свой сервер

- Плюс: один транспорт.
- Минус: режим A («только приложение») остаётся без синхронизации — нарушает равноправие режимов.
