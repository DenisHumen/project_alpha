# ADR-0014: Один процессный runtime ядра и настройки в отдельной SQLite через rusqlite

- **Статус:** Принят
- **Дата:** 2026-11-13
- **Решают:** владелец проекта (решение делегировано агенту, CORE-006)
- **Связано:** `CORE-006`, `CORE-007`, `CORE-011`, `LIB-001`, [ADR-0001](0001-rust-core-uniffi-frb.md), `docs/research/04` §1.4 п.5

## Контекст и проблема

Ядру нужны tokio-runtime, жизненный цикл (foreground, background, shutdown), каталоги данных на 7 платформах и хранилище настроек с миграциями, экспортом и импортом. Это первый крейт, который открывает SQLite, поэтому выбор драйвера задаёт образец для `pa-library`, `pa-jobs` и других. Клиенты (Flutter, Kotlin, Swift) управляют ядром через FFI и не должны держать у себя дескрипторы runtime.

## Факторы решения

- Одна и та же SQLite на Android, Apple (включая tvOS), Windows, Linux и NAS без системной библиотеки.
- Синхронный доступ из FFI-вызовов без async-обвязки; транзакции и `PRAGMA user_version` для миграций.
- Лицензии совместимы с MPL-2.0 и сторами; без OpenSSL.
- Повторный `init` после `shutdown` в том же процессе (Android, тесты).

## Рассмотренные варианты

1. `rusqlite` с `bundled` SQLite.
2. `sqlx` (async, SQLite-драйвер).
3. Системная SQLite (`rusqlite` без `bundled`).

## Решение

Выбран вариант **1 — `rusqlite` + `bundled`**: одна версия SQLite (с `STRICT`, FTS5, WAL) на всех платформах, синхронный API без лишних зависимостей. Тяжёлые запросы крейты выносят в `spawn_blocking` сами.

Конкретика:

- `pa-runtime` владеет одним multi-thread tokio-runtime (по умолчанию не больше 4 рабочих потоков). FFI-фасад держит ровно один экземпляр на процесс (`pa_runtime::global`); после `shutdown` слот освобождается, и `init` запускает новый экземпляр.
- Настройки — отдельный файл `settings.sqlite3` в каталоге `config`, не в БД медиатеки: их можно экспортировать, сбросить или перенести, не трогая библиотеку. Ключ — `[a-z0-9._-]`, значение — JSON. Миграции — список SQL, номер в `PRAGMA user_version`; БД от более новой версии ядра не открывается (защита от даунгрейда).
- Экспорт — JSON `{"format": "kinolune.settings", "version": 1, …}`; импорт атомарный, режимы merge и replace. Секреты в настройках не хранятся (`pa-secrets`, CORE-007).
- Каталоги: десктоп — XDG / `Application Support` / `%LOCALAPPDATA%`; iOS и tvOS — `Library/Application Support` и `Library/Caches` контейнера; Android передаёт `filesDir` и `cacheDir` при `init`.
- Уход в background делает `wal_checkpoint`; подсистемы подписываются на состояние через `watch`-канал.

### Последствия

- Хорошо: один драйвер SQLite для всех крейтов ядра; настройки переживают перезапуск и kill процесса (WAL); простая FFI-модель «init / shutdown».
- Плохо: `bundled` компилирует SQLite из C при каждой чистой сборке (~20 с); глобальный слот означает одно ядро на процесс.
- Требует работы: `LIB-001` использует тот же `rusqlite` из `[workspace.dependencies]`; `CORE-009` заменит упрощённый `CoreError` стабильными кодами ошибок.

## Плюсы и минусы вариантов

### sqlx

- Плюс: async API, проверка запросов при компиляции.
- Минус: тяжелее (макросы, runtime-обвязка), офлайн-режим проверки запросов усложняет CI; SQLite в нём всё равно синхронная под капотом.

### Системная SQLite

- Плюс: меньше время сборки.
- Минус: разные версии на платформах (на Android и Windows своей нет), нет гарантии `STRICT` и FTS5.
