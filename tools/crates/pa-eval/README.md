# pa-eval — eval-раннер распознавания

Прогоняет распознаватель по корпусу [`recognition-eval`](../../recognition-eval/README.md), считает метрики из исследования [03 §6.2](../../../docs/research/03-metadata-recognition.md) и пишет отчёт в JSON и Markdown (задача META-003). Работает офлайн: ответы провайдеров берутся из записанной «кассеты» (record/replay), поэтому отчёт воспроизводится побайтно.

## Запуск

```bash
# отчёт в stdout (Markdown)
cargo run -p pa-eval -- run tools/recognition-eval/examples/examples.jsonl

# отчёт в файлы, с кассетой ответов провайдеров
cargo run -p pa-eval -- run --recognizer naive --tape tape.jsonl \
    --json report.json --md report.md corpus/dev/*.jsonl

# сравнение с сохранённым бейзлайном (CI): код выхода 1 при регрессе
cargo run -p pa-eval -- compare --baseline baselines/main.json --current report.json \
    --max-silent-regression-pp 0.2 --md diff.md
```

Опции `run`: `--recognizer naive|abstain` (по умолчанию `naive`), `--tape FILE`, `--misses FILE` (записать запросы, которых нет на кассете, — по ним строится кассета), `--threshold X` (порог авто, по умолчанию 0.9), `--no-validate` (не проверять корпус валидатором META-001). Код выхода: 0 — ок, 1 — регресс (`compare`), 2 — ошибка аргументов, ввода-вывода или невалидный корпус.

## Как подключить распознаватель

Раннер вызывает трейт `pa_eval::Recognizer`:

```rust
pub trait Recognizer {
    fn name(&self) -> &str;
    fn recognize(&mut self, case: &CaseInput, provider: &mut dyn Provider) -> Vec<FilePrediction>;
}
```

- `CaseInput` — только вход кейса (пути, размеры, длительности, языки, хэши, теги контейнера). Разметку и категории распознаватель не видит.
- `FilePrediction` на каждый файл или каталог диска: `work` (ID работы или `None` — «не знаю»), `episodes` (позиции в любых схемах нумерации), `confidence` в `[0, 1]`, `parse` (разбор имени для метрик парсера).
- Все сетевые запросы — только через `provider`. Распознаватель обязан быть детерминированным: без часов и случайности.

Встроенные бейзлайны нужны, чтобы раннер был проверяем до появления настоящего пайплайна: `abstain` (всё уходит в ручную очередь) и `naive` (грубый разбор имени, один запрос `tmdb/search`, топ-1). Парсер META-005 и пайплайн `pa-recognition` подключаются адаптером к этому трейту.

## Record/replay

Запрос к провайдеру — `ProviderRequest { provider, endpoint, params }`. Кассета — JSONL, строка `{"request": …, "response": …}`, отсортирована по каноническому JSON запроса. `RecordingProvider` оборачивает живой провайдер (META-009 и далее) и пишет кассету, `ReplayProvider` отвечает из неё; запрос, которого нет на кассете, — промах (`tape_misses` в отчёте). Ответ поиска для бейзлайна `naive` нормализован: `{"results": [{"kind", "title", "year", "ids"}]}`.

## Метрики

Элемент — размеченный файл (или каталог диска). Метрики идентификации считаются по **оцениваемым** элементам: у файла есть работа, а у работы — хотя бы один внешний ID.

| Метрика | Определение |
|---|---|
| Решение | `auto` — работа предсказана с `confidence ≥ порога`; `review` — ниже порога; `manual` — распознаватель воздержался |
| Верная работа | есть общее пространство ID, и во всех общих пространствах значения совпадают |
| Precision@auto | верные авто / все авто |
| Coverage | авто / оцениваемые |
| Recall | верные авто / оцениваемые |
| **Тихие ошибки** | неверные авто / оцениваемые — главный KPI (цель ≤ 0,5 %) |
| ECE, reliability | 10 равных корзин уверенности по элементам с предсказанной работой |
| Нагрузка | доли `review` и `manual` |
| Эпизоды | по каждой схеме (`tmdb`, `tvdb_aired`, `tvdb_dvd`, `tvdb_absolute`, `anidb`, `tmdb_group`): схема размечена, если она есть у всех эпизодов файла; верно — при верном авто-матче и совпадении набора позиций |
| Парсинг | точность по каждому размеченному полю `parse` (название — после нормализации) |
| Производительность | число запросов к провайдерам и на 1 000 файлов, промахи кассеты |

Всё считается целиком, по категориям A1–A17 и по типам (`movie`, `show`, `anime`). Время работы печатается в stderr и в отчёт не входит, иначе он не был бы воспроизводимым.

## Отчёт и сравнение

JSON-отчёт содержит сводные метрики, разрезы и исход по каждому элементу (`items`, отсортированы по `case_id`, `path`) — по ним `compare` строит список новых тихих ошибок, новых ошибок и исправлений. Регресс — рост доли тихих ошибок больше чем на `--max-silent-regression-pp` п. п. (по умолчанию 0,2) в целом или в любой категории. В отчёте нет времени, абсолютных путей и случайного порядка: доли округлены до 6 знаков, словари отсортированы.
